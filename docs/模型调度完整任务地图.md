## 3. 目标（M1 模型管理与授权）

1. 在现有「已发现模型」表格中，对真正受当前执行器支持的模型提供独立启用开关。
2. 不可派工、隐藏、内部模型保持只读，不能勾选。
3. 选择保存到现有授权存储，刷新、服务重启后仍保持。
4. 新扫描出来的模型默认不自动获得授权。
5. 兼容已有授权记录，明确处理当前 `explicit=false` 的旧语义，不在升级时意外扩大授权，也不无故中断已有执行任务。
6. 不需要新增独立的模型注册数据库。
7. 重点核实并处理三个真实模型映射问题：
   - Codex：未显式指定模型时，不能绕过逐模型白名单使用 CLI 默认模型。
   - Grok：当前执行器实际固定 `grok-4.7-build-fast`，不得把发现的其他 Grok 模型误当成可以执行。
   - AGY：当前工单使用 3.8f/4a 别名，实际 CLI 使用具体模型和 reasoning 档位。必须让授权粒度和实际派工粒度一致；如采用模型家族授权，应在界面说明，不能把三个 Flash 档位伪装成彼此独立且受到严格授权控制的模型。
- 验收：用户可以选择具体的可执行模型；被关闭的模型不能因为同 Harness 已启用而再次被自动选中。

## 4. 检查并打通现有入口（M2 派工入口）

1. 普通飞书任务自动派工。
2. 用户明确指定模型的任务。
3. 多任务派工中的独立 Harness 约束。
4. 默认 DSH 派工及已有自动评估入口。
5. 工单续接、重试和模型纠错。
6. Worker 实际 CLI 模型绑定。
- 优先复用 `readSelection()`、`isRouteAuthorized()` 和现有执行器规则；避免两套互不一致的授权逻辑。
- 明确区分 Router 自己的运行模型与可授权的 Worker 模型池，不因修改 Worker 白名单而停止 Router 服务。
- 用户明确指定模型时必须遵守该约束；资源耗尽或不可用时，不得未经授权自动切换到其他模型。
- 验收：所有相关入口都遵守同一授权结果，记录的派工模型与实际执行参数一致。

## 5. 额度与重置周期（M3 真实数据源）

- Codex：复用现有 App Server 额度读取器；展示实际返回的额度窗口、剩余比例、窗口周期、下次重置时间、最后更新时间；修复「Harness 状态显示 available，但模型额度区域仍显示 unknown」的不一致；区分账号级与模型级额度。
- DSH/Magpie：复用现有 quota/account/channel 读数；展示能可靠归属的额度、重置时间及来源；不同账号或模型间的数据不能随意合并成虚假总余额。
- Grok、AGY：定向调查现有 CLI 是否有可信、低成本、只读的额度读取方式；找不到就明确显示 unknown 并注明原因；不为了读取额度而发起推理；不接入未经验证的第三方额度服务。
- 更新机制：用户主动扫描刷新；自动派工时按现有机制获取必要的最新资源状态；页面展示上次读取时间；不增加不必要的定时服务或高频轮询。
- 验收：能获取的数据真实、完整、可追溯；不能获取的数据明确未知，不编造数值或重置日期。

## 6. Router 自动调度（M4）

将 M1 已授权模型、M3 资源信息与现有 Router 的 `auto_route`、`rankRouteCandidates()` 连接。对没有明确指定模型的普通任务，Router 应：
1. 根据任务类型、复杂度、读写要求判断候选是否适合。
2. 只从已授权、当前执行器支持的模型中选择。
3. 排除已知额度耗尽、限流、明确不符合任务要求的候选。
4. 参考真实额度、重置时间和用户已有优先级。
5. 没有可信额度时保持 unknown，使用其余真实条件决策，不停止全部派工。
6. 有可靠、可比较的历史质量证据时才参与质量排序。
7. 输出具体选择理由，说明哪些信息已知、哪些未知。
- 不同服务额度单位/周期可能完全不同，不能直接比较百分比。优先复用现有排序和规则，不新增大型打分框架。
- 重点检查：`src/app/resources.ts` 的模型信息是否包含用户已选择的外部模型；`auto_route` 候选是否真正来自合法授权池；无优先级/无质量数据时能否合理可解释派工；只剩一个合法候选时能否派工；用户明确指定模型时是否完全跳过自动改派。
- 验收：模型选择会因任务要求及真实资源状态变化而变化，不再只是固定模型或输入顺序。

## 7. 执行证据（M5）

复用已有 `HarnessRun`、质量记录、`servedModel` 和 Ticket 记录，不另建评价系统。每次真实执行至少保留：任务类型及选模理由、选择的 Harness 和 `requestedModel`、可获取的实际 `servedModel`、执行成功/失败/未验证状态、可验证使用量/实际产物/验收结果。
- 检查任务结束后真实结果能否被后续路由利用；缺少足够质量依据时允许显示「证据不足」，不能因一条任务成功就虚构质量排行。
- 验收：实际记录可追溯；没有质量证据也能正常动态派工。

## 8. 定向验证场景（验收表）

| 场景 | 必须达到的结果 |
| --- | --- |
| 扫描发现新模型 | 列入表格，但不自动授权 |
| 逐模型启用、关闭 | 保存生效，刷新和重启后保持 |
| 关闭 Codex 某个模型 | 自动派工不会再使用它 |
| AGY 别名与实际档位 | 授权与真实执行模型一致 |
| 同名跨 Provider 模型 | 互不串用状态及授权 |
| 额度充足与耗尽 | 合法候选选择按真实状态变化 |
| 重置周期与旧快照 | 正确标记时间和新鲜度，不伪造实时性 |
| 余额不可读取 | 显示 unknown，不编造额度，不误阻断其他合法候选 |
| 普通任务未指定模型 | Router 自动选择并记录理由 |
| 用户明确指定模型 | 不被自动改派 |
| 续接、重试与授权变化 | 遵守当前允许的执行约束 |
| 没有质量样本 | 不虚构评分，仍可派工 |
